# shamsul-server Architecture Documentation

This document describes the design and internal architecture of shamsul-server, a local, offline-first middleware proxy designed to connect the Claude Code CLI (or similar Anthropic API clients) to local Ollama model instances.

## 1. System Overview

shamsul-server sits between the Claude Code client and local Ollama instances. When the Claude Code CLI requests chat completions, shamsul-server intercepts the request and handles it using either a standard local provider or the Multi-Model Bridge orchestration system.




---

## 2. Core Components

### 2.1 FastAPI HTTP Gateway (api/routes.py)
Exposes the Anthropic-compatible Messages API (`/v1/messages`) and the configuration API endpoints. It decodes the incoming requests, invokes the Model Router to select the backend model, and returns a Server-Sent Events (SSE) stream back to the client.

### 2.2 Model Router (api/model_router.py)
Maps requested Claude model names (e.g. `claude-opus-4-8`) to corresponding backend models configured in the environment settings (e.g. `mahbub/hybrid`).

### 2.3 Provider runtime (providers/runtime/)
A dynamic provider cache and factory system that initializes and registers different model completion providers (e.g. Ollama, Gemini, Vercel, and the virtual Mahbub Hybrid provider).

---

## 3. Multi-Model Bridge Orchestration

The Multi-Model Bridge (implemented in `providers/mahbub/client.py`) coordinates multiple specialized models to fulfill a request as if they were a single virtual model.

### 3.1 Two-Stage Pipeline Execution

1. **Lead Reasoning Phase**:
   - The user request is forwarded to the **Bridge Head Model** (default: `ollama/gemma:4b`).
   - The head model is supplied with specific instructions (`instructions.md`) describing how to route the task and how to utilize tools.
   - The head model's reasoning/thinking stream is intercepted, parsed, and forwarded to the client inside a `<thinking>` block.
   - The orchestrator extracts the target executor (`coding` or `tooling`) from the head model's stream via `<delegate>` tags.
   - Any extra reasoning planning output from the head model is collected to serve as guidance for the next phase.

2. **Specialist Execution Phase**:
   - Depending on the delegation decision, the request is routed to:
     - **Coding Model** (default: `ollama/qwen:3.5b`) for writing, editing, or describing code.
     - **Tooling Model** (default: `ollama/gemma:4b`) for searching files or running commands.
   - The guidance text generated by the head model is appended as system prompt context for the target model.
   - The target model's stream is read, and content block indices are dynamically remapped (incremented by 1) to ensure the client receives a sequential, contiguous message stream starting after the initial thinking block.

### 3.2 Tag Stripping Parser (TagStrippingParser)
A custom stream parser that reads incoming tokens chunk-by-chunk. It isolates and extracts `<thinking>...</thinking>` and `<delegate>...</delegate>` tags from the stream dynamically, ensuring that routing directives do not leak to the final user output.

## 4. File Structure

- **api/routes.py**: Contains endpoints for configuration, system status, and Anthropic API handling.
- **config/settings.py**: Handles environment configuration load/save validations using Pydantic Settings.
- **providers/mahbub/client.py**: Core virtual Mahbub Hybrid provider orchestrating the Head, Coding, and Tooling providers.
- **providers/runtime/cache.py**: Caches and resolves active provider clients at request time.
- **providers/runtime/factory.py**: Factory definitions creating instances of provider classes.
- **web/index.html**: Web UI Control Center for updating settings and instructions.
